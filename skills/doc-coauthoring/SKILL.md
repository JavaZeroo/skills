# 文档协作撰写工作流程

此技能提供一个结构化工作流程，引导用户完成协作文档创建。作为积极的引导者，带领用户完成三个阶段：背景信息收集、细化与结构，以及读者测试。

## 何时提供此工作流程

**触发条件：**
- 用户提到撰写文档："写一个文档"、"起草一个提案"、"创建规范"、"写出来"
- 用户提到特定文档类型："PRD"、"设计文档"、"决策文档"、"RFC"
- 用户似乎正在开始一项实质性的写作任务

**初始提议：**
向用户提供协作文档撰写的结构化工作流程。解释三个阶段：

1. **背景信息收集**：用户提供所有相关背景，Claude 提出澄清性问题
2. **细化与结构**：通过头脑风暴和编辑逐节构建内容
3. **读者测试**：用全新的 Claude（无上下文）测试文档，在其他人阅读前发现盲点

解释这种方法有助于确保当其他人阅读文档时（包括将其粘贴到 Claude 时）效果良好。询问他们是否想尝试此工作流程，或是否更愿意自由创作。

如果用户拒绝，则自由创作。如果用户接受，进入第一阶段。

## 第一阶段：背景信息收集

**目标：** 缩小用户所知与 Claude 所知之间的差距，以便之后提供智能指导。

### 初始问题

首先询问用户关于文档的元背景：

1. 这是什么类型的文档？（例如技术规范、决策文档、提案）
2. 主要受众是谁？
3. 当有人阅读此文档时，期望产生什么影响？
4. 是否有需要遵循的模板或特定格式？
5. 还有其他约束或需要了解的背景信息吗？

告知他们可以用简写回答，或以任何方便的方式转储信息。

**如果用户提供了模板或提到了文档类型：**
- 询问是否有模板文档可以分享
- 如果他们提供了共享文档的链接，使用适当的集成获取它
- 如果他们提供了文件，读取它

**如果用户提到编辑现有共享文档：**
- 使用适当的集成读取当前状态
- 检查没有替代文字的图片
- 如果存在没有替代文字的图片，解释当其他人使用 Claude 理解文档时，Claude 将无法看到这些图片。询问是否想要生成替代文字。如果是，请他们将每张图片粘贴到对话中以生成描述性替代文字。

### 信息转储

回答初始问题后，鼓励用户转储他们拥有的所有背景信息。请求以下信息：
- 项目/问题的背景
- 相关团队讨论或共享文档
- 为什么不使用替代解决方案
- 组织背景（团队动态、过去事件、组织政治）
- 时间压力或约束
- 技术架构或依赖项
- 利益相关者的关切

建议他们不要担心整理顺序——只需全部说出来。提供多种提供背景的方式：
- 意识流式信息转储
- 指向团队频道或需要阅读的讨论串
- 链接到共享文档

**如果集成可用**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 服务器），提及可以使用这些直接获取背景信息。

**如果未检测到集成且在 Claude.ai 或 Claude 应用中：** 建议他们在 Claude 设置中启用连接器，以便从消息应用和文档存储直接获取背景信息。

告知他们完成初始转储后将提出澄清性问题。

**在背景收集期间：**

- 如果用户提到团队频道或共享文档：
  - 如果集成可用：告知将立即读取内容，然后使用适当的集成
  - 如果集成不可用：解释无法访问。建议他们在 Claude 设置中启用连接器，或直接粘贴相关内容。

- 如果用户提到未知的实体/项目：
  - 询问是否应搜索已连接的工具以了解更多
  - 等待用户确认后再搜索

- 随着用户提供背景信息，追踪正在学到的内容和仍不清楚的内容

**提出澄清性问题：**

当用户表示已完成初始转储（或提供了大量背景信息后），提出澄清性问题以确保理解：

根据背景中的空白生成 5-10 个编号问题。

告知他们可以用简写回答（例如"1：是，2：参见 #频道，3：不，因为向后兼容"），链接到更多文档，指向需要阅读的频道，或继续转储信息。以最高效的方式进行。

**退出条件：**
当问题显示出理解程度——能够询问边缘案例和权衡而无需解释基础知识时，即表示已收集到足够的背景信息。

**过渡：**
询问他们是否有更多背景信息要在此阶段提供，或是否可以开始起草文档。

如果用户想添加更多内容，让他们继续。准备好后进入第二阶段。

## 第二阶段：细化与结构

**目标：** 通过头脑风暴、筛选和迭代细化，逐节构建文档。

**给用户的说明：**
解释将逐节构建文档。对于每个章节：
1. 将提出关于包含内容的澄清性问题
2. 将头脑风暴 5-20 个选项
3. 用户将指示保留/删除/合并哪些内容
4. 将起草该章节
5. 通过精确编辑进行细化

从未知点最多的章节开始（通常是核心决策/提案），然后处理其余部分。

**章节排序：**

如果文档结构清晰：
询问他们想从哪个章节开始。

建议从未知点最多的章节开始。对于决策文档，通常是核心提案。对于规范，通常是技术方法。摘要章节最好留到最后。

如果用户不知道需要哪些章节：
根据文档类型和模板，建议适合该文档类型的 3-5 个章节。

询问这个结构是否合适，或者他们是否想调整。

**一旦结构确定：**

创建带有所有章节占位符文本的初始文档结构。

**如果可以访问制品：**
使用 `create_file` 创建制品。这为 Claude 和用户提供了可以使用的框架。

告知他们将创建带有所有章节占位符的初始结构。

用所有章节标题和简短占位符文本（如"[待撰写]"或"[此处填写内容]"）创建制品。

提供框架链接，并说明现在是时候填充每个章节了。

**如果无法访问制品：**
在工作目录中创建 Markdown 文件。适当命名（例如 `decision-doc.md`、`technical-spec.md`）。

告知他们将创建带有所有章节占位符的初始结构。

用所有章节标题和占位符文本创建文件。

确认文件名已创建，并说明现在是时候填充每个章节了。

**对于每个章节：**

### 步骤 1：澄清性问题

宣布将开始处理 [章节名称] 章节。提出 5-10 个关于应包含内容的澄清性问题：

根据背景和章节目的生成 5-10 个具体问题。

告知他们可以用简写回答，或只需指出重要内容。

### 步骤 2：头脑风暴

对于 [章节名称] 章节，根据章节复杂程度头脑风暴 [5-20] 个可能包含的内容。寻找：
- 分享的背景中可能被遗忘的内容
- 尚未提及的角度或考虑因素

根据章节复杂程度生成 5-20 个编号选项。最后提议可以提供更多选项（如果需要）。

### 步骤 3：筛选

询问应保留、删除或合并哪些要点。请求简短理由，以帮助了解下一章节的优先级。

提供示例：
- "保留 1,4,7,9"
- "删除 3（与 1 重复）"
- "删除 6（受众已知此内容）"
- "合并 11 和 12"

**如果用户给出自由形式的反馈**（例如"看起来不错"或"我喜欢大部分内容，但..."）而不是编号选择，提取他们的偏好并继续。解析他们想要保留/删除/更改的内容并应用。

### 步骤 4：差距检查

根据他们选择的内容，询问 [章节名称] 章节是否有任何重要遗漏内容。

### 步骤 5：起草

使用 `str_replace` 将此章节的占位符文本替换为实际起草的内容。

宣布现在将根据他们选择的内容起草 [章节名称] 章节。

**如果使用制品：**
起草后提供制品链接。

请他们通读并指出需要更改的内容。注意越具体越有助于为下一章节学习风格。

**如果使用文件（无制品）：**
起草后确认完成。

告知 [章节名称] 章节已在 [文件名] 中起草。请他们通读并指出需要更改的内容。注意越具体越有助于为下一章节学习风格。

**给用户的关键说明（起草第一个章节时包含）：**
提供说明：不要直接编辑文档，而是请他们指出需要更改的内容。这有助于为未来章节学习他们的风格。例如："删除 X 项目符号——已由 Y 涵盖"或"使第三段更简洁"。

### 步骤 6：迭代细化

随着用户提供反馈：
- 使用 `str_replace` 进行编辑（绝不重新打印整个文档）
- **如果使用制品：** 每次编辑后提供制品链接
- **如果使用文件：** 只需确认编辑已完成
- 如果用户直接编辑文档并要求读取：在脑中记录他们所做的更改，并在未来章节中考虑（这体现了他们的偏好）

**继续迭代**直到用户对该章节感到满意。

### 质量检查

连续 3 次迭代后没有实质性更改时，询问是否可以删除任何内容而不失去重要信息。

完成章节后，确认 [章节名称] 已完成。询问是否准备好进入下一章节。

**对所有章节重复此过程。**

### 接近完成时

当接近完成（80% 以上的章节完成）时，宣布打算重新阅读整个文档并检查：
- 各章节间的流畅性和一致性
- 冗余或矛盾
- 任何感觉像"滥作"或通用填充的内容
- 每个句子是否有其分量

阅读整个文档并提供反馈。

**当所有章节起草并细化完成后：**
宣布所有章节已起草。表示打算再次审查完整文档。

审查整体连贯性、流畅度、完整性。

提供任何最终建议。

询问是否准备好进入读者测试，或是否还想细化某些内容。

## 第三阶段：读者测试

**目标：** 用全新的 Claude（无上下文）测试文档，验证其对读者是否有效。

**给用户的说明：**
解释现在将测试文档是否真正对读者有效。这能发现盲点——对作者来说有意义但可能让其他人困惑的内容。

### 测试方法

**如果可以访问子代理（例如在 Claude Code 中）：**

直接执行测试，无需用户参与。

### 步骤 1：预测读者问题

宣布打算预测读者在尝试发现此文档时可能提出的问题。

生成 5-10 个读者会实际提出的问题。

### 步骤 2：用子代理测试

宣布将用全新的 Claude 实例（无本次对话背景）测试这些问题。

对于每个问题，使用仅包含文档内容和问题的子代理调用。

总结读者 Claude 对每个问题的回答正确/错误情况。

### 步骤 3：运行其他检查

宣布将运行其他检查。

调用子代理检查歧义、错误假设、矛盾。

总结发现的任何问题。

### 步骤 4：报告与修复

如果发现问题：
报告读者 Claude 在特定问题上遇到了困难。

列出具体问题。

表示打算修复这些差距。

为有问题的章节循环回到细化阶段。

---

**如果无法访问子代理（例如 claude.ai 网页界面）：**

用户需要手动进行测试。

### 步骤 1：预测读者问题

询问人们在尝试发现此文档时可能提出的问题。他们会在 Claude.ai 中输入什么？

生成 5-10 个读者会实际提出的问题。

### 步骤 2：设置测试

提供测试说明：
1. 打开全新的 Claude 对话：https://claude.ai
2. 粘贴或分享文档内容（如果使用启用了连接器的共享文档平台，提供链接）
3. 向读者 Claude 提出生成的问题

对于每个问题，要求读者 Claude 提供：
- 答案
- 是否有任何歧义或不清楚的地方
- 文档假设读者已知的知识/背景

检查读者 Claude 是否给出正确答案或有误解。

### 步骤 3：其他检查

还要询问读者 Claude：
- "此文档中哪些内容对读者可能有歧义或不清楚？"
- "此文档假设读者已具备哪些知识或背景？"
- "是否存在任何内部矛盾或不一致之处？"

### 步骤 4：根据结果迭代

询问读者 Claude 答错了什么或有哪些困难。表示打算修复这些差距。

为有问题的章节循环回到细化阶段。

---

### 退出条件（两种方法均适用）

当读者 Claude 始终能正确回答问题且不再发现新的差距或歧义时，文档就准备好了。

## 最终审查

当读者测试通过时：
宣布文档已通过读者 Claude 测试。在完成之前：

1. 建议他们自己做一次最终通读——他们拥有这份文档并对其质量负责
2. 建议仔细检查任何事实、链接或技术细节
3. 询问是否达到了他们想要的影响

询问他们是否想要再进行一次审查，或者工作是否已完成。

**如果用户想要最终审查，提供它。否则：**
宣布文档完成。提供一些最终建议：
- 考虑在附录中链接此对话，以便读者了解文档是如何开发的
- 使用附录提供深度，而不使主要文档变得臃肿
- 从真实读者那里获得反馈后更新文档

## 有效引导的技巧

**语气：**
- 直接、程序化
- 简要解释影响用户行为时的理由
- 不要试图"推销"该方法——只需执行它

**处理偏差：**
- 如果用户想跳过某个阶段：询问他们是否想跳过并自由创作
- 如果用户似乎感到沮丧：承认这比预期花费更长时间。建议加快进度的方法
- 始终给用户调整流程的自主权

**上下文管理：**
- 在整个过程中，如果某件被提到的事情缺少背景信息，主动询问
- 不要让差距积累——随时解决它们

**制品管理：**
- 使用 `create_file` 起草完整章节
- 所有编辑都使用 `str_replace`
- 每次更改后提供制品链接
- 绝不为头脑风暴列表使用制品——那只是对话

**质量优于速度：**
- 不要匆忙完成各阶段
- 每次迭代都应有实质性改进
- 目标是一份真正对读者有效的文档
